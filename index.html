Dashboard de Prestaciones Médicas

285 mil prestaciones de 18 meses, consolidadas en un único panel.

Power BISQLDAX
Ver el caso completo

Problema: un centro médico con múltiples sucursales necesitaba visibilidad sobre su actividad mensual (consultas, prácticas, imágenes e infiltraciones) por centro, pero la información vivía dispersa en planillas Excel con datos inconsistentes: nombres de centros y profesionales escritos de formas distintas, espacios y tabulaciones sueltas que rompían cualquier análisis directo.

Qué hice: cargué los datos crudos a SQL para limpiarlos y normalizarlos (formatos de texto inconsistentes, espacios/tabulaciones mal ubicados), y desde ahí conecté Power BI para construir el modelo final.

Insights: el dashboard consolida ~18 meses de actividad (entre sep-2023 y jun-2025) por centro y categoría. Sobre 285 mil prestaciones totales, Centro B concentra la mayor participación (~25%), junto con el Centro H, mientras que Centro G —pese a un volumen menor— muestra el crecimiento relativo más alto (+485%), señal de una sucursal en expansión que antes pasaba desapercibida en las planillas sueltas.

Nota: entre 2024-07 y 2024-11 no se registraron consultas por un corte en el envío de datos desde origen; el salto que se observa en 2024-11 corresponde a la reanudación de los envíos, no a un cambio real de actividad.

Impacto: el equipo dejó de revisar planillas dispersas y ahora cuenta con un panel único, filtrable por fecha/centro/categoría, para monitorear cada sucursal con datos consolidados en vez de estimaciones.

Stack: SQL (limpieza y transformación) · Power BI · DAX

Nota: por confidencialidad, se removió el filtro por profesional y se reemplazaron los nombres reales de los centros por etiquetas genéricas (Centro A, B, C...) para esta muestra. Ambos campos estaban contemplados en el modelo entregado originalmente.

Revenue Analytics CRM

El mismo análisis de revenue replicado en SQL, Python y Power BI para validar consistencia.

PostgreSQLSQLPythonpandasPower BI
Ver el caso completo

Objetivo: recorrer un flujo completo de Revenue Analytics sobre el dataset público CRM Sales Opportunities (Maven Analytics), desde la carga de datos crudos hasta un dashboard ejecutivo, replicando el mismo análisis en 3 herramientas distintas para demostrar consistencia entre ellas.

Qué hice: modelé el dataset en PostgreSQL (con foreign keys entre 4 tablas), hice el EDA y la limpieza en Python (detecté y corregí inconsistencias de escritura que rompían relaciones entre tablas, como "GTXPro" vs "GTX Pro"), escribí queries de negocio en SQL documentadas con su insight, y armé el dashboard final en Power BI.

Insights: revenue total de 10.005.534 sobre 10 meses de operación. GTX Pro es el producto líder, con más de un tercio del revenue total. El win rate está parejo entre productos (60-65%), la diferencia de revenue viene del volumen y precio, no de conversión. El top performer en revenue gestiona un volumen de pipeline mayor que el resto, no convierte mejor que el promedio.

Comparador de precios — Base SEPA

Compara los precios de una lista propia de productos en cuatro cadenas de supermercados.

Pythonpandasrequests
Ver el caso completo

Problema: comparar precios de una lista propia de productos entre supermercados es tedioso: hay que entrar cadena por cadena, buscar cada producto y armar la comparación a mano.

Qué hice: un script en Python que consume la API pública de SEPA (Sistema Electrónico de Publicidad de Precios Argentinos), descarga automáticamente el último relevamiento disponible, lo descomprime y normaliza los datos de cada comercio (Carrefour, Día, Coto, Cencosud) en un dataset único, con comparación de precios por producto y precio promedio entre cadenas.

Próximos pasos: scraping de supermercados que no publican en SEPA, interfaz simple (Streamlit) para no tener que tocar código, e historización de precios para ver evolución en el tiempo.

Finance Tracker

API de 11 módulos con transacciones y cálculo automático de cierres de tarjeta y cuotas.

NestJSTypeORMSQL ServerAngularAngular MaterialRxJS
Ver el caso completo

Motivación: aprender desarrollo full-stack combinando un backend robusto con una interfaz real que lo consume.

Qué hice: el sistema modela ingresos, gastos, compras en cuotas y pagos de servicios, y resuelve un problema no trivial: el cálculo de fechas de cierre y vencimiento de tarjetas de crédito (día fijo del mes o reglas relativas, como "el segundo jueves de cada mes"), con prorrateo automático de cuotas.

Funcionalidades: dashboard con resumen mensual por categoría, formulario dinámico según tipo de transacción, vista de cuotas pendientes con filtros, y cierre anual automático vía cron job.

Aprendizaje: cómo estructurar una API con transacciones de base de datos (commit/rollback) para operaciones que tocan varias tablas, y cómo separar responsabilidades entre backend y frontend cuando la lógica de negocio es compleja.
